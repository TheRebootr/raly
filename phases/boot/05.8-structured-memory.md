# Phase 5.8: Structured Memory (Inspired by memubot)

## Context

Phase 5.5 gives Boot raw conversation history — a message log per project. That's necessary
but limited: Boot can recall *what was said* but not *what it learned*. A user mentioning
"I prefer tabs over spaces" on Monday gets forgotten by Thursday unless it's still in the
context window.

This phase adds a **structured knowledge layer** inspired by
[memubot](https://github.com/seigneurcui/memubot) (Apache 2.0). memubot's architecture is
pure Python orchestration over LLM calls — no proprietary code, no paid libraries, no black
boxes. We adapt the *patterns*, not the code (memubot targets Python 3.13, uses OpenAI SDK,
requires pgvector for production — none of which fit our stack).

### What We Take from memubot

- **Hierarchical memory model**: Categories → Items (with typed memories)
- **Memory type taxonomy**: profile, knowledge, preference, behavior, skill
- **Extract pipeline pattern**: conversation → LLM extraction → structured items → categorize → persist
- **Dual retrieval**: embedding similarity (fast) + LLM ranking (accurate)
- **Protocol-based DB interface**: clean abstraction, already proven with SQLite

### What We Don't Take

- PostgreSQL / pgvector (we use SQLite)
- OpenAI SDK / lazyllm / langchain-core (we use Claude Code CLI)
- Rust/PyO3 scaffolding (placeholder code, irrelevant)
- Python 3.13 requirement (artificial, driven by Rust ABI flag)
- Multi-tenant user scoping (Boot is single-user)
- Resource/blob storage (Boot doesn't ingest images/video/audio yet)

## Architecture Position

```
Phase 5.5 (foundation):
  conversations table → raw message log per project
  session.py → active project tracking

Phase 5.8 (this phase, sits on top):
  conversations table → INPUT: raw messages feed extraction pipeline
                              ↓
  knowledge.py → LLM extracts structured memories from conversations
                              ↓
  memory_items table → structured facts, preferences, skills, etc.
  memory_categories table → named buckets (e.g. "coding style", "project context")
                              ↓
  retrieval → context injection into Claude CLI calls (alongside raw history)

Data flow:
  User message → executor.py → Claude response
       ↓                              ↓
  Phase 5.5 saves raw history    Phase 5.8 (async, background):
                                   extracts knowledge from the exchange
                                   stores as structured memory items
                                        ↓
  Next request → executor.py builds context:
    1. Project CLAUDE.md (Phase 5.5)
    2. Relevant structured memories (Phase 5.8) ← NEW
    3. Recent conversation history (Phase 5.5)
    4. User's current message
```

## Data Model

SQLite tables in the shared `boot.db` (same file as sessions, conversations, audit_log).

```sql
-- Typed memory items extracted from conversations
CREATE TABLE IF NOT EXISTS memory_items (
    id TEXT PRIMARY KEY,                    -- UUID
    memory_type TEXT NOT NULL,              -- profile | knowledge | preference | behavior | skill
    summary TEXT NOT NULL,                  -- Human-readable description of the memory
    source_project TEXT,                    -- Which project this was learned in (NULL = global)
    embedding BLOB,                         -- Optional: serialized float array for similarity search
    happened_at TEXT,                       -- When the memory was formed
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%f', 'now')),
    updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%f', 'now'))
);

-- Named categories for organizing memories
CREATE TABLE IF NOT EXISTS memory_categories (
    id TEXT PRIMARY KEY,                    -- UUID
    name TEXT NOT NULL UNIQUE,              -- e.g. "coding preferences", "project goals"
    description TEXT,                       -- What this category covers
    embedding BLOB,                         -- For category-level similarity matching
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%f', 'now'))
);

-- Many-to-many: items belong to categories
CREATE TABLE IF NOT EXISTS memory_category_items (
    category_id TEXT NOT NULL REFERENCES memory_categories(id),
    item_id TEXT NOT NULL REFERENCES memory_items(id),
    PRIMARY KEY (category_id, item_id)
);

CREATE INDEX IF NOT EXISTS idx_items_type ON memory_items(memory_type);
CREATE INDEX IF NOT EXISTS idx_items_project ON memory_items(source_project);
```

### Memory Types (adapted from memubot)

| Type | What It Captures | Example |
|------|-----------------|---------|
| `profile` | Facts about the user | "Uses Arch Linux (Omarchy), Mac Mini 2018" |
| `knowledge` | Domain facts learned during work | "Project X uses FastAPI + SQLAlchemy" |
| `preference` | User preferences and opinions | "Prefers tabs, dislikes over-engineering" |
| `behavior` | Patterns in how the user works | "Usually works on 2-3 projects per session" |
| `skill` | Techniques/patterns Boot has learned | "This user's Docker images use multi-stage builds" |

## Pipeline (High Level)

### 1. Extract (after each conversation exchange)

Runs **asynchronously** after executor.py returns a response. Does not block the user.

- Input: the user message + Claude's response (one exchange)
- LLM call: ask Claude to extract structured memories from this exchange
- Output: zero or more `MemoryItem` candidates
- Dedup: compare against existing items (simple text overlap or embedding similarity)
- Persist: insert new items into `memory_items`

### 2. Categorize (piggybacks on extraction)

- For each new item, find or create appropriate category
- Can be LLM-assisted ("which category does this belong to?") or rule-based by type
- Start simple: auto-categories by memory_type, let it evolve

### 3. Retrieve (before each Claude CLI call)

- Input: the user's current message
- Query relevant memories (by project, by type, by similarity)
- Format as structured context block
- Inject into Claude CLI call alongside conversation history

### Retrieval Strategy (start simple, evolve)

**V1 — keyword + type filtering (no embeddings):**
- Filter by current project + global memories
- Filter by memory_type relevant to the task
- Recent memories weighted higher
- Inject top N items as structured context

**V2 — add embedding similarity:**
- Embed user query + memory summaries (using Claude or a local model)
- Cosine similarity for retrieval
- numpy for vector math (memubot's approach, minimal dep)

**V3 — LLM-assisted retrieval (memubot's dual approach):**
- Ask Claude to rank/filter retrieved memories by relevance
- Only if V1/V2 retrieval quality is insufficient

## What This Phase Does NOT Cover

- Multi-user memory isolation (Boot is single-user, single-tenant)
- Image/video/audio memory extraction (text conversations only)
- External knowledge base ingestion (only learns from conversations)
- Memory editing UI (user can't manually add/edit/delete memories via Telegram yet)
- Distributed workflow runners (memubot supports Temporal/Burr — overkill for Boot)
- LangChain/LangGraph integration (unnecessary abstraction layer)

## Open Questions (resolve during implementation)

1. **Extraction cost**: Every conversation exchange triggers an LLM call for extraction.
   Is this acceptable on a subscription plan? Throttle to every N exchanges? Only extract
   from "interesting" conversations (>3 turns)?

2. **Embedding provider**: Claude API doesn't have a public embedding endpoint. Options:
   a. Use Claude CLI to "describe this memory in 3 keywords" (poor man's embedding)
   b. Use a free/local embedding model (e.g. sentence-transformers via Python)
   c. Skip embeddings entirely in V1, use keyword/type filtering only

3. **Memory staleness**: Preferences change. How do we handle contradictions? memubot has
   a dedup/merge step (currently placeholder). Start with "latest wins" for same-type
   items about the same topic?

4. **Context budget**: Phase 5.5 already injects conversation history (~4000 chars).
   How much budget does structured memory get? Need to balance history vs. knowledge
   vs. the actual user message.
