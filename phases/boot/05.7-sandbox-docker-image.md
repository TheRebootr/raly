# Phase 5.7: Sandbox Docker Image (Dockerfile.sandbox)

## Context

RALY's Boot harness executes Claude Code CLI tasks inside ephemeral Docker
containers. Each task spawns a fresh container that is destroyed after completion.
This phase builds the Docker image used for those sandbox containers. The image must
contain Claude Code CLI and nothing else — no network tools, no package managers,
no unnecessary binaries. Defense in depth beyond the `--network none` and `--read-only`
runtime flags applied by executor.py (Phase 5.4).

Architecture position:

```
executor.py
    ↓ docker run ... boot-sandbox:latest claude --print "<message>"
    ↓
┌──────────────────────────────────────────┐
│  boot-sandbox:latest (THIS IMAGE)        │
│  - Claude Code CLI installed             │
│  - Minimal base (no curl, wget, etc.)    │
│  - Non-root user baked in               │
│  - No network tools (defense in depth)   │
│  - Read-only root at runtime             │
│  - /workspace mounted at runtime         │
└──────────────────────────────────────────┘
```

## Prerequisites

- Phase 2 complete: Docker daemon hardened, `python:3.12-slim` pulled and scanned
- trivy installed (from Phase 2)

## Critical Design Decision: Network Access

**Problem:** Claude Code CLI needs to reach the Anthropic API (`api.anthropic.com`).
The spec calls for `--network none`. These are mutually exclusive.

**This decision MUST be resolved before building this image.**

Options (research before choosing):

### Option A: Allow restricted network access

Instead of `--network none`, create a Docker network that only allows traffic to
Anthropic's API endpoints:

```bash
# Create restricted network
docker network create --driver bridge boot-restricted

# Use iptables to restrict to Anthropic IPs only
# NOTE: This is fragile — IP addresses can change
```

In executor.py: `--network boot-restricted` instead of `--network none`

Pros: Claude CLI works normally inside container
Cons: Network access exists (reduced isolation), IP-based filtering is fragile

### Option B: Run Claude CLI on host, sandbox file operations only

- Claude CLI runs on the host (network access available)
- Only file read/write operations happen inside the container
- Container is used for filesystem isolation, not execution

Pros: Clean separation, true network isolation for file ops
Cons: More complex architecture, Claude runs with host privileges

### Option C: Use Claude Code's built-in sandbox

- Claude Code CLI may have built-in sandbox support (`/sandbox` mode)
- May use bubblewrap on Linux for filesystem + network isolation
- Could replace our Docker wrapping entirely

Pros: Maintained by Anthropic, purpose-built
Cons: Less control, may not exist or be sufficient

### Option D: Proxy model — preferred if feasible

- Container has `--network none`
- Claude CLI is configured to use a local proxy on the host
- Proxy is accessible via Docker's host gateway
- Proxy only forwards to `api.anthropic.com`

```
Container (--network none except host gateway)
    → host proxy (localhost:8080)
    → api.anthropic.com (only allowed destination)
```

In executor.py: `--add-host=host.docker.internal:host-gateway`
Pros: Container is nearly air-gapped, only controlled API access
Cons: Requires running a proxy, additional complexity

**Document the chosen approach in `~/boot-src/ARCHITECTURE-DECISIONS.md`**

## Implementation Specification

### Dockerfile

The exact Dockerfile depends on the network decision. Here is the base structure
that applies regardless:

```dockerfile
# Pin the base image by SHA256 digest for reproducibility
# Get digest: docker inspect python:3.12-slim --format '{{.RepoDigests}}'
FROM python:3.12-slim@sha256:<recorded-digest-from-phase-2>

# Metadata
LABEL maintainer="RALY"
LABEL purpose="Claude Code CLI sandbox"

# Security: remove unnecessary packages and tools
RUN apt-get update && \
    apt-get remove -y --purge \
        curl \
        wget \
        netcat-openbsd \
        net-tools \
        iproute2 \
        iputils-ping \
    && apt-get autoremove -y \
    && apt-get clean \
    && rm -rf /var/lib/apt/lists/* \
    && rm -rf /usr/bin/curl /usr/bin/wget /usr/bin/nc 2>/dev/null

# Install Claude Code CLI
# Method depends on how Claude Code CLI is distributed:
# Option 1: npm (if it's a Node.js tool)
# RUN apt-get update && apt-get install -y --no-install-recommends nodejs npm && \
#     npm install -g @anthropic-ai/claude-code && \
#     apt-get remove -y nodejs npm && apt-get autoremove -y && \
#     rm -rf /var/lib/apt/lists/*

# Option 2: pip (if it's a Python package)
# RUN pip install --no-cache-dir claude-code

# Option 3: Binary download (if distributed as standalone binary)
# COPY claude /usr/local/bin/claude
# RUN chmod +x /usr/local/bin/claude

# Create non-root user
RUN groupadd -g 1000 claude && \
    useradd -u 1000 -g 1000 -m -s /bin/bash claude

# Create workspace mount point
RUN mkdir /workspace && chown 1000:1000 /workspace

# Set home directory for Claude CLI config
ENV HOME=/home/claude

# Switch to non-root user
USER 1000:1000

WORKDIR /workspace

# No CMD — executor passes the command at runtime
```

### What to Research About Claude Code CLI

Before finalizing the Dockerfile, the subagent MUST determine:

1. **How is Claude Code CLI installed?**
   - `npm install -g @anthropic-ai/claude-code`?
   - `pip install claude-code`?
   - Standalone binary?
   - Which runtime does it need? (Node.js, Python, or self-contained?)

2. **How does it authenticate?**
   - `ANTHROPIC_API_KEY` environment variable?
   - `~/.claude/` config directory?
   - OAuth flow (unsuitable for container)?
   - Claude Pro subscription binding (session-based)?

3. **What does `--print` flag do exactly?**
   - Single-shot mode (send prompt, get response, exit)?
   - Does it need internet access at runtime?
   - Does it use the Anthropic API or a local model?

4. **What filesystem does it need at runtime?**
   - Does it write to `~/.claude/` or `~/.config/`?
   - Does it need `/tmp`?
   - What directories must be writable?

5. **Does Claude Code have a built-in sandbox?**
   - The `--sandbox` flag (if it exists)
   - bubblewrap integration on Linux
   - Can it layer with our Docker isolation?

### Image Verification Tests

```bash
# Test 1: Non-root user
docker run --rm boot-sandbox:latest whoami
# Expected: claude

# Test 2: No network tools
docker run --rm boot-sandbox:latest which curl wget nc nmap 2>&1
# Expected: not found for all

# Test 3: No package manager access (in read-only mode)
docker run --rm --read-only boot-sandbox:latest apt-get update 2>&1
# Expected: failure (read-only filesystem)

# Test 4: Claude CLI present
docker run --rm boot-sandbox:latest claude --version
# Expected: version number

# Test 5: Workspace writable
docker run --rm -v /tmp/test-workspace:/workspace:rw boot-sandbox:latest \
    touch /workspace/test-file
# Expected: success, file created

# Test 6: Root filesystem read-only
docker run --rm --read-only boot-sandbox:latest touch /test-file 2>&1
# Expected: Read-only file system

# Test 7: Full sandbox test (as executor would run it)
mkdir -p /tmp/sandbox-test
echo "print('hello')" > /tmp/sandbox-test/test.py
docker run --rm \
    --network none \
    --read-only \
    --memory 2g \
    --cpus 2 \
    --pids-limit 256 \
    --cap-drop ALL \
    --security-opt no-new-privileges:true \
    --user 1000:1000 \
    --tmpfs /tmp:rw,noexec,nosuid,size=256m \
    -v /tmp/sandbox-test:/workspace:rw \
    boot-sandbox:latest \
    ls /workspace/
# Expected: lists test.py
```

### Image Rebuild Process

Monthly rebuild to pick up security patches:

```bash
# Pull latest base image
docker pull python:3.12-slim

# Record new digest
docker inspect python:3.12-slim --format '{{.RepoDigests}}'

# Update Dockerfile with new digest
# (edit the FROM line)

# Rebuild
docker build --no-cache -f Dockerfile.sandbox -t boot-sandbox:latest .

# Scan
trivy image boot-sandbox:latest

# Test (run verification tests above)

# Remove old image
docker image prune -f
```
